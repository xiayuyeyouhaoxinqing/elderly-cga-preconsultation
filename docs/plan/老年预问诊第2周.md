## 首批接口与已确认口径

- 职工通过 `POST /api/patients/{patient_id}/outpatient-encounters` 为已建档患者登记，传入 `department_name`。重复登记返回 409。通过 `POST /api/patients/outpatient-encounters/{encounter_id}/close` 结束。
- 患者按已确认的身份证号和登记手机号核验。登录请求可明确指定 `encounter_kind=outpatient`。旧调用未指定时优先匹配住院，没有在院记录时匹配门诊。
- 当前门诊开放本人任务列表及按本次就诊鉴权的传统问卷接口。住院专用功能及门诊代理授权、AI 采集暂不开放。
- 已复查当前仓库全部分支。既有提交包含已发布列表查询，模板含离线导入命令，尚未找到量表上传 HTTP 接口。因此上传、审核及发布作为待实现工作跟踪。

## 会话修复与真实服务验证

- 患者列表和任务详情在 API 模式下使用服务端核验的结果。任一页面收到 401 后停止轮询，清空当前患者身份、任务及本地草稿等缓存，返回身份核验页。旧请求完成后不会写回已经失效的会话。
- 本机一次性环境使用 PostgreSQL 16.15 和 Redis 7.4.3 Windows 移植版。通过 `alembic upgrade head` 初始化空数据库，再启动真实 FastAPI 服务。所有病例均为合成数据。
- 并发用例先持有患者行锁，同时提交两条登记请求，通过 `pg_stat_activity` 确认两条请求均等待锁后释放。结果为 HTTP 200 和 409，数据库只保留一条进行中记录。另验证职工登录、患者 HttpOnly Cookie、Redis 会话及 TTL、门诊结束后返回 401、退出后删除会话键。
- 390px Edge 连接真实 FastAPI、PostgreSQL 和 Redis。使用两个独立浏览器会话分别停留在任务列表和详情，职工关闭门诊后，两端均清空缓存并回到登录页。再访问原详情地址时不展示任务。
- 后端含真实服务的专项和既有患者管理回归共 19 项通过。前端 74 项测试、Lint、类型检查和构建通过。
- 复测时将 `APP_DATABASE__*` 和 `APP_REDIS__*` 指向一次性的回环服务，数据库名须以 `cga_week2_test` 开头，Redis 使用独立端口。执行 `uv run alembic upgrade head`，设置 `TEST_WEEK2_LIVE_SERVICES=1` 后运行 `uv run pytest tests/integ-test/test_outpatient_portal_live.py -q`。用例会写入合成记录，勿接入共享或正式数据库。
